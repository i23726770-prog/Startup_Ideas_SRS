# Проектирование логической модели и нормализация базы данных

## 1. Исходная структура данных

На начальном этапе предметная область системы Startup Ideas SRS рассматривается как единая структура, содержащая сведения о пользователях, идеях, категориях, статусах, приоритетах и планах реализации.

При хранении всех сведений в одной таблице возникли бы избыточность данных и аномалии обновления. Например, имя и электронная почта пользователя повторялись бы для каждой его идеи, а информация о категории дублировалась бы во всех записях с этой категорией.

Для устранения этих проблем была выполнена нормализация базы данных.

## 2. Первая нормальная форма (1НФ)

Для приведения данных к первой нормальной форме были выполнены следующие действия:

- Каждое поле содержит одно значение.
- У каждой таблицы определён первичный ключ.
- Повторяющиеся группы данных вынесены в отдельные таблицы.
- Цели и этапы реализации плана хранятся отдельными записями, а не списками внутри одного поля.

Для хранения целей создана таблица `PlanGoals`, а для хранения этапов — `PlanStages`.

Таким образом, данные имеют атомарную структуру и соответствуют требованиям 1НФ.

## 3. Вторая нормальная форма (2НФ)

Для соблюдения второй нормальной формы необходимо, чтобы каждый неключевой атрибут полностью зависел от первичного ключа.

В разработанной базе данных для каждой таблицы используется отдельный первичный ключ из одного поля. Поэтому частичные зависимости от составного первичного ключа отсутствуют.

Данные пользователей, категорий, статусов и приоритетов вынесены в самостоятельные таблицы. Это позволяет избежать повторения соответствующей информации в таблице `Ideas`.

Таким образом, структура соответствует требованиям 2НФ.

## 4. Третья нормальная форма (3НФ)

Для соблюдения третьей нормальной формы необходимо исключить транзитивные зависимости между неключевыми атрибутами.

В разработанной модели справочная информация вынесена в отдельные таблицы:

- `Users` — сведения о пользователях;
- `Categories` — названия и цвета категорий;
- `Statuses` — названия статусов;
- `Priorities` — названия приоритетов.

В таблице `Ideas` хранятся внешние ключи, ссылающиеся на соответствующие таблицы.

Планы реализации вынесены в таблицу `Plans`. Цели и этапы каждого плана хранятся отдельно в таблицах `PlanGoals` и `PlanStages`.

Это позволяет избежать дублирования данных и обеспечивает логическое разделение сущностей.

Таким образом, разработанная структура соответствует требованиям 3НФ.

## 5. Итоговая логическая модель

В результате нормализации сформирована реляционная модель, состоящая из восьми таблиц:

1. `Users` — пользователи системы.
2. `Ideas` — идеи стартапов.
3. `Categories` — категории идей.
4. `Statuses` — статусы идей.
5. `Priorities` — приоритеты идей.
6. `Plans` — планы реализации идей.
7. `PlanGoals` — цели планов.
8. `PlanStages` — этапы планов.

Связи между таблицами реализованы с помощью внешних ключей.

Итоговая модель приведена к третьей нормальной форме (3НФ), что уменьшает избыточность данных и помогает избежать аномалий при добавлении, изменении и удалении записей.
## 6. Связи между таблицами

В разработанной базе данных определены следующие связи:

- `Users` → `Ideas` — один пользователь может иметь несколько идей.
- `Categories` → `Ideas` — одна категория может использоваться несколькими идеями.
- `Statuses` → `Ideas` — один статус может быть назначен нескольким идеям.
- `Priorities` → `Ideas` — один приоритет может использоваться несколькими идеями.
- `Ideas` → `Plans` — одна идея может иметь несколько планов реализации.
- `Plans` → `PlanGoals` — один план может содержать несколько целей.
- `Plans` → `PlanStages` — один план может содержать несколько этапов.

Связи реализованы с помощью первичных и внешних ключей.
